# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

DiskMaster is a Windows Forms disk-usage scanner. It walks a folder tree on a background thread, accumulating file counts/sizes per folder, and reports progress back to the UI. Three projects, referenced via `DiskMaster.slnx`:

- **DiskMasterLib** (`net10.0`) — the scan engine. Platform-agnostic, no UI dependencies.
- **MainForm** (`net10.0-windows`, WinForms) — the UI, references `DiskMasterLib`.
- **DiskMasterLib.Tests** (`net10.0`, xUnit) — tests `DiskMasterLib` only, via its public API.

## Commands

- Build: `dotnet build` (from repo root; builds all three projects via `DiskMaster.slnx`)
- Run: `dotnet run --project MainForm`
- Test: `dotnet test` (or `dotnet test --filter FullyQualifiedName~TestName` for a single test)

## Architecture

### `FolderExplorer` (DiskMasterLib) — the scan engine

`FolderExplorer` owns a dedicated background thread (`_scanningThread`, started in the constructor) that walks folders pulled from a `ConcurrentStack<ScanningNode>` (a *stack*, deliberately — see below). It's a small state machine over `RunState` (`WaitingForRun → Running ⇄ Paused (via PausePending) → Stopped/Completed/Aborted`, controlled via `Run()` / `Pause()` / `Stop()` / `Dispose()`).

Thread signaling uses two small wrapper types instead of raw `ManualResetEvent`/flags:
- `ThreadWaiter` — wraps `ManualResetEvent` with `SetWait()`/`SetNoWait()` naming, since `ManualResetEvent`'s own "signaled = don't wait" polarity reads backwards.
- `EventFlag` — a `Volatile`-backed boolean flag (`_stopFlag`, `_disposeFlag`).

The scan pipeline itself is `ThreadMain()` → `RunScanLoop()` → `TryScanFiles()` / `EnqueueChildFolders()` per folder. Each loop iteration in `RunScanLoop` checks `_disposeFlag` / `_stopFlag` / queue-empty before popping the next folder — when touching this method, keep each exit path (`Stopped`, `Completed`, disposed) symmetric: every path that stops the loop must also re-arm `_threadWaitForRunWaiter` via `SetWait()`, or the thread will spin instead of blocking on the next `Run()`.

Three per-node stats roll up to every ancestor as they're found, mirroring each other: `AddFileStatsToTree()` (called from `TryScanFiles`) adds a folder's own file bytes/count to itself and every ancestor's `FileBytes`/`FileCount` — both are *inclusive* of the node's own files. `AddFolderCountToTree()` (called from `EnqueueChildFolders`, once per batch of newly-discovered children rather than once per child, for one O(depth) walk instead of several) adds to `FolderCount` on the node *and* its ancestors — subfolders are "beneath" their parent too, transitively — but `FolderCount` is *exclusive* of the node itself, since a folder isn't beneath itself. Don't conflate the two conventions when adding another rolled-up stat.

`_pendingFolders` is a `ConcurrentStack`, not a queue, so the scan is depth-first: it fully finishes one branch before starting the next sibling, rather than working level-by-level. This matters for the live tree view — depth-first means the "actively scanning" branch stays put and grows deeper instead of jumping between unrelated top-level folders. `EnqueueChildFolders` pushes a folder's newly-discovered children in *reverse* order so the first-discovered child (the first one shown in the tree) ends up on top of the stack and is popped first — a plain forward push would scan the *last* child first instead, since a stack is LIFO. `ScanningNode.Children` still lists children in natural discovery order regardless; only the stack push order is reversed.

`ScanningNode.InProgress` tracks whether a folder or anything beneath it is still being scanned — set `true` at node creation, cleared by `MarkScanComplete()` once none of a node's direct children are still in progress (a child's own `InProgress` already recursively encodes its whole subtree, so checking only direct children is enough). `MarkScanComplete(currentNode)` must be called at every point in `RunScanLoop` where a node finishes being handled — currently three: the excluded-folder skip, a failed `TryScanFiles`, and after `EnqueueChildFolders` on the success path. Miss one of those and its ancestors never clear `InProgress`. Folders still queued when `Stop()`/`Dispose()` cuts a scan short are intentionally left `InProgress = true` — never processed, never completed.

`FolderExplorer`'s three callbacks (`onRunStateChanged`, `onNodeUpdated`, `onScannerCompleted`) are invoked directly from the scanning thread, not marshaled anywhere — any UI consumer must dispatch to its own thread itself (see `MainForm.Invoke(...)` usage).

`C:\Windows` is hardcoded as an excluded folder (`ExcludedFolder` const in `FolderExplorer`) — it's skipped entirely, not descended into.

`FolderExplorer.SkippedFolderCount` tracks folders left out of the totals — the excluded-folder skip, or a folder whose files/subfolders threw `UnauthorizedAccessException`/`IOException` (both already caught and recorded on the node as `ScanError`; this just also counts them). A non-elevated scan of a real Windows drive will always undercount actual disk usage by whatever's in inaccessible folders (`C:\Program Files\WindowsApps`, `System Volume Information`, etc.). The property is tracked and tested (`DiskMasterLib.Tests`) but **not currently surfaced anywhere in `MainForm`'s UI** — it was briefly shown as a `"(N folders skipped)"` note next to the size, but that was explicitly removed at the user's request. If it needs to come back, this is where the data already lives.

`FolderExplorer.CurrentlyScanningNode` is the *one* node the scanning thread is actively working on right now (or null when nothing's running) — set right after each `TryDequeue` in `RunScanLoop`, before that node is processed. It's distinct from `InProgress`: `InProgress` stays true for a node's entire subtree duration (ancestors included), while `CurrentlyScanningNode` identifies specifically which single node is being worked on at this instant — that's what lets a UI distinguish "actively scanning this one" from "just waiting" for everything else that's still `InProgress`. A plain field with `Volatile.Read`/`Write` is enough (no lock) since it's only ever written by the scanning thread and reference assignment is atomic.

### `ScanningNode` (DiskMasterLib, internal) — the folder tree

Each scanned folder is a `ScanningNode`, forming a tree via `Parent`/`Children`. `ScanningNode.Empty` is a shared sentinel used to terminate parent-walks (`while (parentNode != ScanningNode.Empty)`) — it's self-referencing (`Empty.Parent == Empty`), which is set up explicitly in a static constructor rather than via field initializer, because a field initializer runs before the static `Empty` field itself is assigned and would otherwise capture `null`.

The public-facing `IScanningNode` interface exposes a read-only subset (`FolderName`, `FileBytes`, `InProgress`, `Children`, `Parent`) for consumers outside the library; `ScanningNode` itself is `internal`. `Children` is the one place a genuine cross-thread hazard exists — the scanning thread appends to it (`ScanningNode.AddChild`, called from `EnqueueChildFolders`) while a UI consumer might enumerate it — so it has two views: an unlocked `internal Children` for the scanning thread's own same-thread reads (e.g. `MarkScanComplete`'s `Any(...)`), and an explicit `IScanningNode.Children` implementation that takes a lock and returns a `ToArray()` snapshot for everyone else. `Parent` needs no lock despite also being cross-thread-readable: it's set once at construction and never reassigned, and it's only ever handed to another thread via a node that already came out of the locked `Children` snapshot, whose acquire/release provides the memory barrier for the whole object, not just `_children`. `IScanningNode.Parent` is null for the root (same "expose null instead of the internal `Empty` sentinel" pattern as `FolderExplorer.RootNode`, which likewise needs no lock — `_rootNode` is only ever touched from whichever thread calls `Run()`, always the UI thread in this app).

### `MainForm` (WinForms) — the UI

`Program.cs` wires everything through `Microsoft.Extensions.Hosting`'s generic host: `FolderExplorerFactory` is a singleton, `MainForm` is transient, resolved once and passed to `Application.Run`.

`MainForm` creates its `FolderExplorer` in its constructor via the injected `FolderExplorerFactory`, wiring its three callbacks. Since those callbacks fire on the scanner's background thread, every UI-touching handler wraps its work in `Invoke(...)`.

`MainForm_FormClosing` cancels the first close attempt and calls `_folderExplorer.Dispose()` instead; the actual `Close()` happens once the scanner thread reports `RunState.Aborted` back through `OnScannerRunStateChanged`, so the form only closes after the background thread has actually exited. Note for anyone testing this closing behavior programmatically: calling `Close()` without an active message loop pumping (e.g. `Application.Run` or repeated `Application.DoEvents()`) deadlocks, since the scanning thread's `Aborted` callback goes through a blocking `Invoke` back to the UI thread — harmless under normal `Application.Run`, but a trap for one-off diagnostic/test harnesses that call `Close()` directly.

`FormatBytes` (binary/1024-based: KB/MB/GB/TB) and `FormatCount` (decimal/1000-based: K/M/B, used for folder/file counts everywhere - the status bar totals and each tree node's counts) share one non-obvious detail: a plain `< nextTierThreshold` switch arm isn't enough, because a value just below the threshold can *round* up to it at 2 decimal places (e.g. `1048575` bytes is `< Mb` but `1048575/Kb` rounds to `1024.00`, which would otherwise print the nonsensical `"1024.00 KB"` instead of rolling over to `"1.00 MB"`). Both guard against this with `Math.Round(value / divisor, 2) < nextTierThreshold` instead. Keep that guard if either method's tiers ever change.

`BtnRun_Click` reads the root folder from `CmbRootFolder.Text` (validated with `Directory.Exists` first, showing a `MessageBox` instead of starting a doomed scan if it's missing) rather than a hardcoded path. `CmbRootFolder` is an editable `ComboBox` pre-populated in `PopulateRootFolderChoices()` from `DriveInfo.GetDrives().Where(d => d.IsReady)`, defaulting to `Path.GetPathRoot(Environment.SystemDirectory)` (the actual system drive, not an assumed `C:\`) — the user can also type a path directly, or use `BtnBrowse` (`FolderBrowserDialog`, `ShowNewFolderButton = false`) to pick any folder, not just a drive root. Both the combo box and browse button are disabled outside `WaitingForRun`/`Stopped`/`Completed` in `UpdateActionButtonStates` — deliberately *excluding* `Paused`, since `FolderExplorer.Run()`'s resume path (`state == Paused`) ignores its `rootFolder` argument entirely, so letting the user change the selection while paused would be misleading (it wouldn't take effect until a fresh run).

The form's layout is plain `Dock`-based, no manual `Anchor` math: `PanelButtons` (a `FlowLayoutPanel`, `Dock = Top`, `AutoSize = true`) holds the folder picker row (`LabFolderPrompt`, `CmbRootFolder`, `BtnBrowse`) followed by Run/Pause/Stop — narrow enough and it wraps to a second line via the panel's default `WrapContents`, which is fine, not a bug; `StatusStripMain` (`Dock = Bottom`) holds the six live status labels as `ToolStripStatusLabel`s (`Ssl*` prefix, `Current folder` deliberately last per an explicit user request) with `BorderSides = Right` on the rest for visual separation between segments; `TvFolderView` (`Dock = Fill`) takes whatever's left. Control add order in `InitializeComponent` matters for this to lay out correctly — the `Fill` control must be added to `Controls` *before* the `Top`/`Bottom`-docked ones, or it won't correctly exclude their space (verified empirically; WinForms dock-layout priority follows Z-order, and each `Controls.Add` call moves that control to the front of Z-order, so later-added controls claim their edge space first, leaving the *earlier*-added `Fill` control whatever's left).

`StatusStrip` does **not** wrap or shrink items to fit available width — an item whose natural (`AutoSize`) width doesn't fit just renders past the strip's right edge instead of truncating, effectively invisible despite `Visible == true` and `IsOnOverflow == false`. This bit `SslCurrentFolder` directly: being the last item (unbounded-length folder path) meant a sufficiently deep path could push it off the visible strip entirely. Fixed two ways, deliberately redundant: `SslCurrentFolder.Spring = true` (the standard StatusStrip idiom for "let one item claim leftover space" — note this only *grows* an item into unused space, it does **not** shrink/truncate one that's already too wide, so it alone would not have fixed this) plus `TruncatePathForStatusBar()` in `MainForm.cs` capping the displayed path to 60 characters (keeping the tail, e.g. `"...Cache\Even\Deeper"`, since the most specific part of a path is the most useful part when something has to give). If `ToolStripStatusLabel` bounds ever need checking again, be aware that a headless `Form.PerformLayout()` + `Application.DoEvents()` diagnostic (which worked fine for verifying the plain `Dock`-based `Panel`/`TreeView` layout above) did **not** reliably reflect `StatusStrip`'s internal item layout even after explicitly calling `StatusStripMain.PerformLayout()`/`.Refresh()` and pumping the message loop repeatedly — trust real interactive testing over that technique for this specific control type.

`FolderTreeController` (`MainForm/FolderTreeController.cs`) drives `TvFolderView` as a virtual tree: only currently-visible `TreeNode`s are ever materialized (a lone dummy placeholder child, `Tag == null`, gives a node an expand arrow without materializing its real children — the standard WinForms lazy-tree trick, since `TreeView` has no built-in virtual mode). Unlike the rest of `MainForm`, it doesn't hook any of `FolderExplorer`'s background-thread callbacks — it instead polls on a UI-thread-only `Timer` (~300ms), reading `RootNode`/`CurrentlyScanningNode`/`Children`/`InProgress`/`FileBytes` directly each tick. That avoids `Invoke` marshaling entirely and is cheap specifically because virtualization keeps the visible-node count small. A node's own `Children` list is final the moment it's ever visible at all (a parent's `EnqueueChildFolders` always finishes fully before any of its children can be seen), so the only thing the poll ever needs to add reactively is an expand arrow on a child that just went from "no known children" to "some" — never re-populate an already-shown list.

Each node is one of three states (`FolderTreeController.NodeState`): `Completed` (`!InProgress`, shows its final size and counts), `Scanning` (`InProgress` and on the active scan path, shows its size/counts-so-far plus "(Scanning...)") or `Pending` (`InProgress` but not on it, nothing shown but the name - the counts would just be zero, not worth displaying). "On the active scan path" means the node *or any of its ancestors* is `CurrentlyScanningNode` — `IsOnActiveScanPath` walks up from `CurrentlyScanningNode` via `Parent` checking for a match, so the whole branch from the root down to whatever's actively being scanned shows `Scanning`, not just that one leaf — and since `FileBytes`/`FileCount`/`FolderCount` all keep rolling up live via `AddFileStatsToTree`/`AddFolderCountToTree` regardless of state, every node on that branch (root included) shows growing running totals, not just the leaf actually being read right now. A plain `TreeNode` can only have one color for its whole text, so this needs an owner-drawn `TreeView` (`DrawMode = OwnerDrawText` + `DrawNode`). Rather than two hardcoded segments, `NodeDisplay` holds an ordered list of `(Text, Color)` runs that `OnDrawNode` just loops over, measuring and drawing each left to right — `BuildNodeDisplay` is the single source of truth for both `TreeNode.Text` (`NodeDisplay.FullText`, which the control still needs for layout even in owner-draw mode) and those colored runs. Size and counts are visually distinct on purpose, not just by color: folder name stays the tree's normal color; size is colored by scan state (`SizeColor` once `Completed`, `ScanningColor` while active) since it's the primary, live-changing figure; counts (`"{folders} folders, {files} files"`) get their own fixed `CountsColor` and are grouped in parens *after* the size, separated by extra space — the grouping, not just the color, is what actually makes size and counts easy to tell apart at a glance (color alone was tried first and wasn't enough, since size and counts used to share one color). `CountsColor` was deliberately chosen distinct from `PendingColor`/`ScanningColor`/`SizeColor` so it doesn't accidentally read as a scan-state indicator.

**Hot-path highlighting**: `TryBuildHotPathSegment` adds an optional `"(N.N% of disk)"` segment — a node's `FileBytes` as a percentage of the *whole disk's* capacity (`_diskSizeBytes`, from `DriveInfo(...).TotalSize` on the scanned root's drive, cached in `SeedTree` per run; 0 - so the segment just never appears - if `DriveInfo` can't make sense of the root, e.g. a UNC path), not the scan total, so it stays meaningful for a subfolder scan too. Shown only once it rounds to `WarmFraction` (1%) or more, colored `WarmColor` (`IndianRed`) or, past `HotFraction` (5%), `HotColor` (`Firebrick`) — a deliberately different hue family from the other four colors on the line so it never reads as a scan-state or counts indicator. This needed no new bookkeeping to highlight *multiple* hot spots rather than just the single biggest path: since `FileBytes` already rolls up cumulatively to every ancestor, a huge folder three levels down automatically makes its parent, grandparent, etc. show an elevated percentage too — expanding toward any consistently-elevated branch leads to a hot spot, and there can be several live at once, wherever they are in the tree. The percent-vs-threshold comparison rounds *before* comparing (`Math.Round(percent, 1)` against `WarmFraction * 100`/`HotFraction * 100`), not after — same rounding-vs-threshold pitfall as `FormatBytes`/`FormatCount`: comparing the raw fraction let two values that both display as "5.0%" land on opposite sides of the Warm/Hot cutoff and show different colors for identical text.

`OnDrawNode` checks `e.State.HasFlag(TreeNodeStates.Selected)` and, when set, draws every segment in `SystemColors.HighlightText` instead of its own color — `OwnerDrawText` mode already paints the selection background (`SystemColors.Highlight`) for us before `DrawNode` runs, and several of the per-segment colors tuned for a white background are a poor (in `CountsColor`'s case, near-unreadable blue-on-blue) contrast against it. This is the same thing every native control does for selected rows; don't add per-color contrast tweaks instead - swapping to `HighlightText` wholesale is simpler and matches system behavior.

Every place `FolderTreeController` mutates more than one `TreeNode` at once (`OnTimerTick`'s whole body, and each of `OnBeforeExpand`/`OnAfterCollapse`) wraps the work in `_treeView.BeginUpdate()`/`EndUpdate()` — without it, each individual `.Text` change or `Nodes.Add()`/`Clear()` repaints immediately, and since several visible nodes (the whole active-scan branch) typically change on the same 300ms tick, those repaints visibly stacked up as flicker. `TreeView.BeginUpdate`/`EndUpdate` are **not** reference-counted (unlike, say, nested `SuspendLayout`) — they just toggle `WM_SETREDRAW` directly, so a nested `EndUpdate()` re-enables repainting early rather than waiting for an outer one. That's why `PopulateChildren` itself doesn't wrap its own `Nodes.Clear()`/`Add()` calls: it's only ever invoked from inside one of the three already-wrapped call sites above, and adding its own pair would prematurely close the outer one. Keep that invariant if `PopulateChildren` ever gets a new caller.

`BeginUpdate`/`EndUpdate` alone wasn't enough — it reduces how *often* the control repaints, not *how* each repaint happens, and a second, worse flicker remained: a top-to-bottom gradient where the lowest visible rows flashed far more than the top ones. That's the signature of missing double buffering — each row's background-erase and owner-drawn-text repaint land as two separate visible frames instead of one atomic swap, and that lag compounds down the visible list. The usual WinForms fix, subclassing to set the protected `Control.DoubleBuffered = true`, is a well-documented dead end for `TreeView` specifically: it only affects WinForms' own `OnPaint` pipeline, and `TreeView` delegates its actual rendering to the native Win32 `SysTreeView32` control underneath, which that property doesn't touch. `EnableNativeDoubleBuffering()` instead P/Invokes `SendMessage(hwnd, TVM_SETEXTENDEDSTYLE, TVS_EX_DOUBLEBUFFER, TVS_EX_DOUBLEBUFFER)` — the actual documented way to double-buffer the native control — deferring via `HandleCreated` if the control's Win32 handle doesn't exist yet (it usually doesn't at `FolderTreeController` construction time, since that runs before the form is shown). Verified by reading the flag back with `TVM_GETEXTENDEDSTYLE` after the call, not just assumed from the P/Invoke succeeding.

### `DiskMasterLib.Tests` — testing approach

There's no file-system abstraction in `FolderExplorer` (it calls `Directory.GetFiles`/`GetDirectories` directly), so tests run against small real folder trees created under the OS temp directory rather than mocks — see the `TempFolderTree` helper in `FolderExplorerTests.cs`.

`FolderExplorer` never blocks and reports everything through its three constructor callbacks on its own scanning thread, so tests can't assert immediately after calling `Run()`. The `ScanHarness` helper in the same file wraps a `FolderExplorer`, records what its callbacks report under a lock, and exposes polling waits (`WaitForState`, `WaitForCompleted`) plus optional `OnStateChanged`/`OnNodeUpdated` hooks.

Those hooks exist to deterministically hit otherwise-racy states on tiny/fast trees: since `SetRunState` invokes `onRunStateChanged` *synchronously* before returning, a hook that calls e.g. `Pause()` the instant it sees `RunState.Running` is guaranteed to catch that state — see `Pause_ThenResume_CompletesScan`, `Run_WhileRunning_Throws`, and `Stop_LeavesUnprocessedFoldersInProgress` for the pattern (the last one hooks `onNodeUpdated` instead, which fires synchronously on the *scanning* thread). Don't reach for `Thread.Sleep`-based timing to hit a specific state — it's flaky for trees this small; use the reentrant-callback trick instead.
